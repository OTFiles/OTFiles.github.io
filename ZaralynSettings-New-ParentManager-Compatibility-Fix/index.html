ZaralynSettings 适配新版家长管理——机制迁移分析与自动识别实现

ZaralynSettings 适配新版家长管理（v6.2.8）：机制迁移分析与自动识别实现

前言

此前发布的 《某学习平板自由安装软件——ParentManager的SQL注入漏洞》 分析了家长管理应用 ParentManager 的 AppContentProvider SQL 注入漏洞，并基于该漏洞开发了工具 ZaralynSettings（解除安装限制、黑白名单管理、数据库管理）。

然而当家长管理升级到 v6.2.8 后，旧版工具的关键功能失效了：黑名单/白名单写入了错误的表、全局安装开关不再生效。本文记录了对新版 6.2.8 的逆向分析结论、新旧版本机制差异，以及 ZaralynSettings 如何通过”自动识别 + 版本路由”兼容新旧两个版本。

一、新旧版本机制差异

1.1 安装管控机制的迁移（核心差异）

对 家长管理_v6.2.8.apk 解包逆向（apktool）并与旧版对比，发现安装/使用管控的核心表发生了迁移：

功能 老版本 新版 6.2.8
黑名单/白名单 forbidden_app（state: 0=黑/1=白） install_app_list（disabled_state: 0=允许/1=禁止）
全局安装开关 un_mall_app_state（state: 0=禁/1=允） 仍存在，但仅剩云同步使用
家长密码 user_info.password 明文 明文（中间版本曾 AES 加密，密钥硬编码）
数据库 app_record.db（AppContentProvider） 同左，表结构扩充

新版 AppContentProvider$DBHelper 创建的核心表：

新版自带 UI（AllowAppsFragment/DisallowAppsFragment/MenuFragment）全部基于 install_app_list.disabled_state：

而旧的 forbidden_app / un_mall_app_state 仅剩 SyncDataService（云同步）和 ParentApplication 引用，不再是管控主路径。

1.2 禁用状态的下游消费者

disabled_state 被多个组件实时消费（这也是为什么修改后立即生效）：

  • AppLockService：应用启动时 disabledState == 1 → 弹出家长密码验证拦截
  • RecordService：定期检查运行中的应用，disabledState == 1 → 杀掉最近任务、加入限制表
  • ControlSettingsFragment：渲染每个应用的开关状态
  • SyncDataService：把 disabledState 映射为 appState 回传服务端

1.3 SqliteProvider 只读

com.coolerfall.Provider.SqliteProvider（authority com.readboy.parentmanager.SqliteProvider）在新版中 insert/update/delete 直接返回 null/0，仅 query 可用。其数据库 mysql.db3 是从 assets 复制的静态分类表（FirsType/SecondType 等），本身没有可写价值。

二、多种修改 SQL 的方式（已在 6.2.8 验证）

# 方式 说明
1 raw_sql 任意 SELECT content://.../AppContentProvider/raw_sql，selection 参数直接进 rawQuery()，可带 PRAGMA
2 标准 ContentProvider CRUD content://.../AppContentProvider/<表名> 的 insert/update/delete 操作任意表（如直接改 user_info.password）
3 SqliteProvider 只读查询 mysql.db3 静态数据
4 非 SQL 攻击面 RecordServiceBinder.allowPackage() 无认证白名单注入、HIDE_APPS_EVENT 广播等

注意：raw_sql 是 rawQuery，只适合 SELECT；写入必须走标准 CRUD。中间版本家长密码曾用 AES 加密存储（密钥 #reaboy+ZHdream# 硬编码，KeyGenerator + SecureRandom(种子) 弱派生），6.2.8 已恢复明文存储与 String.equals() 比对。

三、兼容层设计（ZaralynSettings v66+）

3.1 版本自动识别

以 install_app_list 表结构作为新旧判据（两个版本都存在该表，但列集不同）：

探测顺序（关键：先直接 content 查询，再包管理诊断）：

  1. raw_sql PRAGMA 探测列结构
  2. 回退：标准查询 sqlite_master（app_record.db → mysql.db3）
  3. 全部失败才进入包管理诊断（扫描候选 Provider、检查包是否禁用）

识别结果只缓存确定值（OLD/NEW），UNKNOWN 每次启动重新探测——避免家长管理后装/启用后检测失效。

3.2 功能按版本路由

功能 老版 新版 6.2.8
全局安装开关 un_mall_app_state.state install_app_list 全表 disabled_state 批量置 0/1 + 兼容写旧门禁
白名单 forbidden_app state=1 install_app_list.disabled_state=0（upsert，双写 forbidden_app）
黑名单 forbidden_app state=0 install_app_list.disabled_state=1（同上）
家长密码 user_info 明文读取 明文读取 + AES 密文解密回退

3.3 SQL 修改方式全局设置

新增设置项（SharedPreferences 持久化，全局生效）：

  • 自动（推荐）：查询优先 raw_sql，写入走标准 CRUD
  • raw_sql 注入：仅通过 raw_sql 执行查询（数据库管理仅支持 app_record 库）
  • 标准 ContentProvider：完全不依赖 raw_sql，全部走标准增删改查

四、踩坑记录

4.1 检测不到已安装的家长管理

现象：设备上家长管理正常运行，但工具提示”未检测到家长管理/检测失败”，日志显示全量扫描 0 个候选。

根因（两处）：

  1. Android 11+ 包可见性：工具 targetSdk 34，未声明 <queries>/QUERY_ALL_PACKAGES 时，resolveContentProvider()/getInstalledPackages() 根本看不到家长管理这个包
  2. 强制停止状态：getInstalledPackages 默认不包含被 force-stop 的应用，需加 MATCH_UNINSTALLED_PACKAGES 标志

修复：

  • Manifest 声明 QUERY_ALL_PACKAGES + <queries>（包名 + provider authority）
  • 探测顺序反转：先直接发 content 查询（ContentResolver 按 authority 解析，不受包可见性影响），失败才走包管理诊断

4.2 UNKNOWN 结果被持久化缓存

旧实现把探测失败的结果也写入 SharedPreferences，导致之后每次启动都直接返回”未检测到”，必须手动重测。修复：只缓存 OLD/NEW，UNKNOWN 每次启动重新探测。

4.3 文件日志系统

为了在无 logcat 的环境下排查（学习平板不方便连 adb），为工具增加了文件日志：

  • 按日期分文件：Android/data/com.readboy.installer/files/logs/yyyy-MM-dd.log
  • 内置「日志」页面：◀▶ 切换日期、一键复制
  • 版本探测、Provider 解析、所有数据库操作均落盘

4.4 GitHub Actions 构建排查

本地环境无法编译（SDK/Java 兼容问题），改用 GitHub Actions 构建。构建失败时无法直接下载日志（需管理员权限），于是在 workflow 中增加”构建失败自动上传 build-output.log artifact”，从而定位到 CONTENT 模式路由中残留的已删除常量引用（Unresolved reference: AUTHORITY）。

五、使用方式

  1. 从 Releases 下载最新 APK（标题”修复新版兼容性问题”）
  2. 安装到学习平板
  3. 「设置」页查看自动识别的家长管理版本（老版/新版）与 Provider 包名
  4. 「设置」页可切换全局 SQL 修改方式（默认自动）
  5. 「日志」页可查看/复制运行日志

总结

新版家长管理（6.2.8）把安装/使用管控从 forbidden_app + un_mall_app_state 迁移到了 install_app_list.disabled_state，但 AppContentProvider 的 raw_sql 任意 SQL 执行与无权限保护问题依旧存在。ZaralynSettings 通过”表结构探测自动识别版本 + 功能按版本路由 + 全局 SQL 方式设置”兼容了新旧两个版本，并借由文件日志系统解决了无 adb 环境下的排障问题。
