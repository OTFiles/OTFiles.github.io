解绑、重新绑定与云端配置拉取：家长管理（6.2.8）的身份与同步机制详解

适用版本：家长管理 v6.2.8（家长管理_v6.2.8.apk）
分析方法：apktool 反编译 + smali 逐行核对（与旧文档交叉验证，一切以 6.2.8 为准）

开篇：一张图看懂三件事

  • ① 解绑 = 让平板与家长账户”离婚”（服务端解除绑定 + 本地数据全清）
  • ② 重新绑定 = 用激活码”复婚”（重新激活，恢复管控）
  • ③ 拉配置 = 平板定期/按事件从云端”抄作业”（把家长手机上的设置抄到本地）

一、解绑逻辑链（完整链路）

1.1 什么是”解绑”

家长管理有一个”家长端 App”和一个”平板端 App”，两者通过一个 uid（8 位数字设备号） 绑定。解绑就是：

  1. 服务端把平板从家长账户下移除（cancel_bindings 接口）
  2. 平板本地数据全部清空（密码、管控列表、使用记录）
  3. 之后家长手机 App 再也管不到这台平板

1.2 解绑的完整触发链（从按钮到服务器）

第一步：UI 入口（需要家长密码）

解绑不是随便能点的——入口藏在家长管理 App 的设置里，点击后弹出密码确认框（PassWordDialog）。输入正确的家长密码后，才走到下一步。（密码比对直接读本地 user_info 表的 password 字段，明文 equals 比较。）

第二步：PromptDiaLog 确认弹窗

密码验证通过后，弹出 PromptDiaLog 确认框，点确认后连发三个广播给 SyncDataService：

第三步：SyncDataService 收到 ACTIONG_RESET

SyncDataService 是家长管理的”调度中心”，它把广播翻译成内部消息：

第四步：SyncHandler 发解绑请求（关键）

请求参数（身份凭证）：signature（MD5 签名）+ imei（设备序列号）+ timestamp + app_id=parent-manage

第五步：本地数据全清（解绑的”物理清除”）

无论服务器响应成功与否，客户端都会执行本地清理（在发送请求后立即执行）：

1.3 解绑链路的”漏洞视角”（对小白的关键提示）

⚠️ 已确认的缺陷：解绑动作本身不校验密码！

SyncDataService 是 exported=true 且无权限保护的服务。任何 App（包括恶意 App）都可以直接发 ACTIONG_RESET 广播触发解绑，完全绕过密码对话框：

也就是说：解绑的”密码验证”只存在于 UI 层，服务层没有任何身份验证。这是家长管理防护措施设计缺陷之一（详见《家长管理防护措施设计缺陷补充报告》缺陷五）。

二、重新绑定逻辑链

2.1 解绑后的平板状态

解绑后平板处于”未激活”状态：

  • 本地密码已清空（user_info 空）
  • 管控列表已清空
  • 激活状态标记 rby_pad_activate_state 仍保留（但服务端已解绑）

注意：解绑后平板不会自动进入”可用”状态，反而可能因为云端同步（拉取配置）把服务端最新的管控拉回来，恢复限制。

2.2 重新绑定流程（激活码方式）

第一步：弹出激活对话框

ActivationDialog（输入激活码的弹窗）由 ActivationActivity 承载，在需要激活时弹出。

第二步：输入激活码

家长在家长端 App 里生成一个 激活码（active_code），在平板上输入。激活码是重新绑定的”钥匙”。

第三步：发送激活请求

请求的”身份凭证”放在 HTTP Header 里（与解绑不同，激活用 Header 而非 Body 参数）：

Header 值
signature MD5 签名（getSign2）
imei 设备序列号
timestamp 时间戳
app_id parent-manage
active_code 激活码（核心凭证）

第四步：激活成功

激活状态写入 **Settings.Global("rby_pad_activate_state")=1**——这是系统级设置，不只是应用私有数据。

第五步：恢复同步

激活成功后，SyncDataService 会立即触发配置拉取（见第三部分），把家长在手机端设置的管控重新拉到本地，平板恢复”受管”状态。

2.3 重新绑定的关键限制

限制 说明
需要激活码 激活码由家长端生成，没有激活码无法重新绑定
激活接口是 HTTP http://parent-manage.readboy.com/api/v1/machine/active（非 HTTPS）
激活码走 Header 但签名算法已泄露（密钥硬编码在 APK 里），可伪造
激活状态系统级 rby_pad_activate_state 在 Settings.Global，普通 App 无法改（需要系统权限）

三、什么时候家长管理会从云端拉取配置？

这是本议题的核心。**”拉取配置”= 调 jpush/content 接口（GetOnlineAppResponse2），把服务端管控数据整体下载并覆盖本地。**

3.1 拉取配置的完整触发时机表（按触发频率排序）

# 触发时机 触发方式 拉取模式
1 服务启动（开机/被杀重启） SyncDataService.onStartCommand → 200ms 后发 MSG_GET_ONLINE_APPS(0x4) 全量
2 推送注册成功 RPushReceiver（极光推送回调）→ ACTION_GET_ONLINE_DATA 全量
3 网络恢复（断网→联网） NetWorkStateReceiver（CONNECTIVITY_CHANGE）→ ACTION_GET_ONLINE_DATA_WHEN_ONLINE + ACTION_SYNC_INIT_AND_SEND + ACTION_GET_PASSWORD 全量
4 UI 手动操作 家长端 App 里各种”刷新/设置”操作 → ACTION_GET_ONLINE_DATA 全量（带 get_all flag 可强制全量）
5 密码同步后 ACTION_NOTIFY_PASSWORD_CHANGE → 触发重新拉取 全量
6 解绑/重置后 ACTION_CHECK_ONLINE_DATA → 触发检查 全量
7 心跳（10 分钟） MSG 0x30 → UploadHeartBeatResponse → /api/v1/heart_beat 仅心跳，不拉配置！

3.2 关键澄清：10 分钟心跳 ≠ 拉配置

之前旧文档的结论在 6.2.8 中再次验证正确：

  • 每 10 分钟（600000ms）发一次心跳请求 http://parent-manage.readboy.com/api/v1/heart_beat
  • 心跳参数：signature + imei + timestamp + app_id + screen_off
  • 心跳响应只解析 status==1（设备在线），不解析任何配置数据，也不触发全量拉取

通俗理解：心跳是”报平安”，不是”抄作业”。抄作业只发生在 3.1 表的 1-6 号事件。

3.3 全量拉取的执行（GetOnlineAppResponse2）

MSG_GET_ONLINE_APPS(0x4) → SyncHandler.pswitch_50 → 构造 GetOnlineAppResponse2：

响应回来后，逐项覆盖本地数据库（这就是”云端说了算”）：

通俗理解：每次全量拉取，服务端都把”标准答案”抄给平板，平板无条件覆盖本地。

3.4 上传方向（本地 → 云端）

本地状态也会上传（UploadOnlineAppTask）：把 online_control_app 表的变更（add/update/delete）上传到云端。上传操作同样用 signature 签名。

四、子议题一：通过修改数据库解除已管控应用，可行吗？限制是什么？

4.1 可行性：可行（短期有效）

直接修改 install_app_list 表的 disabled_state（1=禁用 → 0=正常），可以让某个应用立即解除管控。因为：

  • 管控的执行端（AppLockService 等）直接读本地 install_app_list 表，改了就生效
  • 修改方式：用本工具（ZaralynSettings）或直接 SQL 改

4.2 限制：会被”全量拉取”覆盖（关键限制）

最大的限制是：任何一次全量拉取都会把服务端的管控状态重新写回本地，覆盖你的修改！

触发覆盖的事件（再次强调）：

  • 开机/服务重启（100% 触发）
  • 推送到达（家长在手机端操作后，很快推送）
  • 网络重连
  • 家长端 UI 操作
  • 密码同步

通俗理解：你改了本地数据库 = 在”考试答案”上涂改，但平板每次”抄作业”（拉配置）都会把正确的标准答案抄回来，把你的涂改覆盖掉。

4.3 限制的量化

限制因素 覆盖周期
服务重启/开机 立即覆盖（200ms 后拉取）
家长手机端操作 推送到达后立即覆盖（通常秒级~分钟级）
网络重连 重连后立即覆盖
心跳 不覆盖（只报平安）

4.4 实践建议（小白向）

  • 临时解除：改库 → 立即使用（几分钟到几十分钟内有效），但别指望长期
  • 长期解除：需要同时阻止”拉配置”（如断网/改 hosts/阻止 SyncDataService），或者修改后立刻断网使用
  • 配合工具：本工具（ZaralynSettings）的”解除管控”功能就是改 disabled_state，其效果同样受拉取覆盖限制

五、子议题二：通过修改数据库强制”不可输入密码”为”可输入密码”，可行吗？限制是什么？

5.1 先搞清楚”不可输入密码”是什么

家长管理 App 里有一个开关控制”是否允许输入密码”（即能否设置家长密码）。这个开关存在 user_info 表的 is_allow_input_pwd 字段：

5.2 可行性：改库”看起来”可行，但有两个硬限制

硬限制 1：密码会被云端覆盖

全量拉取（GetOnlineAppResponse2）时，服务端下发的密码会无条件覆盖本地：

也就是说：

  • 你改了 is_allow_input_pwd=1，但服务端 password 对象一下发，密码相关字段全被覆盖
  • 服务端下发空密码 → 本地密码被清空（delete()）
  • 服务端下发非空密码 → 本地密码被替换为服务端密码

硬限制 2：is_allow_input_pwd 本身可能不参与 UI 判断

反编译显示：is_allow_input_pwd 字段在客户端只有 Helper 层的读写，没有任何 UI 代码直接消费它（即”是否允许输入密码”的判断逻辑可能不在本地，而在服务端响应/其他逻辑里）。这意味着改这个字段可能根本不生效（改了个寂寞）。

结论：**”强制可输入密码”在 6.2.8 中改库基本无效**，因为：
① 密码字段每次全量拉取被覆盖
② 允许输入密码的判定可能不在本地

5.3 密码相关字段速查

字段 含义 谁写 改库效果
password 家长密码（明文） 设置密码时写；拉配置时覆盖 改了会被覆盖
is_long_pwd 是否长密码 设置密码时写；拉配置时覆盖 同上
is_allow_input_pwd 是否允许输入密码 只有 Helper 读写，无 UI 消费 改库可能无效
state 状态 多种 未知

5.4 真正可行的替代思路（小白向提示）

既然”改库”受限于云端覆盖，更实际的思路是：

  1. 临时改：改 is_allow_input_pwd=1 + 改 password 为空 → 立即在 UI 设置密码 → 设置完成后马上断网（防止拉取覆盖）
  2. 利用工具：ZaralynSettings 的”读家长密码”功能直接读 user_info.password（明文），不需要改任何东西就能知道密码
  3. 注意：6.2.8 密码是明文存储，但中间版本是 AES 加密（密钥硬编码），工具已做兼容

所有涉及”身份”的操作，都依赖同一套签名体系：

6.1 签名算法（getSign2）

6.2 各操作的身份凭证对比

操作 接口 凭证位置 凭证内容
心跳 /api/v1/heart_beat Body signature + imei + timestamp + app_id
拉配置 /api/v1/jpush/content Body signature + imei + timestamp + app_id + get_all
解绑 /v1/machine/cancel_bindings Body signature + imei + timestamp + app_id
激活（重新绑定） /api/v1/machine/active Header signature + imei + timestamp + app_id + active_code
密码上传 /api/v1/password/upload Body signature + imei + timestamp + app_id + password + is_long_pwd
密码拉取 GET_PASSWORD 广播 - 走 SyncDataService

6.3 身份鉴别的核心结论（小白版）

  1. 所有接口都靠”签名”自证身份，没有 token/会话，签名 = 时间戳 + 硬编码密钥的 MD5
  2. 密钥硬编码在 APK 里 → 任何会反编译的人都能伪造签名（签名形同虚设）
  3. 唯一”真人凭证”是激活码（active_code）——重新绑定必须有它，但它走 HTTP（可被中间人截获）
  4. 设备身份 = imei（序列号）+ uid（8位数字），uid 存外部存储 /.readboy/profile/userInfo.txt，可被修改
  5. **激活状态 = Settings.Global("rby_pad_activate_state")**，系统级，普通 App 改不了

八、”禁止输入密码”是怎么来的？（完整链路）

接第五议题：之前说过 is_allow_input_pwd 无 UI 消费，那”禁止输入密码”到底由什么控制？
答案：由云端下发的一个字段 allow_input_pwd 控制，落到本地 SharedPreferences，再由多个 UI 组件消费。

8.1 一句话结论

“本机禁止输入密码” = 云端在拉取配置（jpush/content）时下发 allow_input_pwd.status != 1，客户端把它翻译成本地开关 no_allow_input_pwd = true（SharedPreferences），密码弹窗/键盘/服务全部按此开关执行拦截。

8.2 完整链路（从云端到 UI）

8.3 证据（smali 逐行）

第一步：云端字段解析（GetOnlineAppResponse2.smali 5362 行起）

第二步：密码弹窗消费（passwordlayout 库 PasswordDialog.smali 890 行）

第三步：UI 表现（pw_dialog_password.xml 布局）

禁止状态下，密码弹窗显示：

  • 锁图标 + 「平板管控」+ 「本机已禁止使用密码解锁」（rl_disallow_input_password 布局，默认 gone，禁止时显示）
  • 底部提示条：「根据管控策略，本机禁止输入密码」

第四步：键盘层拦截（KeyboardFrameLayout2.smali 404 行）

第五步：密码输入框拦截（PassWordDialog$6.smali 81 行）

第六步：后台服务同步（RecordService.smali 15434 行）

第七步：数据库列同步（UserInfoHelper.smali 334 行）

8.4 关键结论（小白版）

  1. “禁止输入密码”完全由云端说了算：家长在手机 App 端设置（或服务端策略），下一次拉配置时下发 allow_input_pwd.status，客户端无条件执行
  2. 本地开关是 SharedPreferences("my_pref_data") 里的 no_allow_input_pwd（布尔值）
  3. 系统级联动：同时写 Settings.Global("rby_enable_start_machine_by_password")——即”禁止输入密码”连开机用密码解锁也一起禁止
  4. user_info.is_allow_input_pwd 列只是同步展示：它由本地开关同步而来，改它不影响任何判断（真正的开关在 SharedPreferences 和 Settings.Global）
  5. 改库”强制可输入密码”为什么无效：真正的开关不在数据库里，而在 SharedPreferences（my_pref_data.xml 文件）和 Settings.Global——而且每次拉配置都会被云端重新覆盖

8.4.1 实测确认：改数据库无效，改 SharedPreferences 文件才有效（附证据）

疑点：”既然校验不联网、开关在本地，那直接改数据库 user_info 表不就行了？”
结论：不行——数据库里那列（is_allow_input_pwd）没有任何代码读它做判断，它是”镜像”。真正的开关在 SharedPreferences 文件里。

证据 1：存储位置 = SharedPreferences 文件，不是数据库

证据 2：所有密码拦截点都读 SharedPreferences，不读数据库

消费端 读什么 行为
PasswordDialog（密码弹窗） my_pref_data 的 no_allow_input_pwd 直接显示「本机已禁止使用密码解锁」
KeyboardFrameLayout2/3（键盘层） 同上 按键被吞 + Toast「根据管控策略，本机禁止输入密码」
PassWordDialog$6（输入框） 同上 输入文字被清空
RecordService（后台） 同上 周期同步到 Settings.Global

证据 3：数据库列是”没人看的镜像”

  • 写入方向：UserInfoHelper 写库时从 SharedPreferences 同步过来（UserInfoHelper.smali 334 行）
  • 读取方向：UserInfo.getIs_allow_input_pwd() 全工程无任何调用者（grep 为空）
  • 结论：改数据库这列 = 改了个没人读的值，无效

证据 4：谁写真正的开关？只有云端拉取

  • 全工程唯一写入方：GetOnlineAppResponse2.smali（5399/5431 行，allow_input_pwd 分支）
  • 其余全部是读（PassWordDialog / KeyboardFrameLayout / RecordService / UserInfoHelper）
  • 所以：不联网 = 开关不会被改 = 改了能持续生效

8.5 想真正”解除禁止输入密码”？（实测操作）

按生效优先级（从易到难）：

方法 操作 能撑多久

两个必须记住的限制：

  1. 必须重启进程：SharedPreferences 有内存缓存，只改文件不重启不会生效（force-stop 后启动 = 重新从文件加载）
  2. 联网即失效：只要下次拉配置（开机 / 推送到达 / 网络恢复 / UI 操作），云端把 allow_input_pwd.status 下回非 1，开关立刻被写回 true

最佳实践组合：断网 → force-stop → 改 XML → 重启家长管理 → 保持断网使用。只要不触发拉配置，”可输入密码”就一直有效。
